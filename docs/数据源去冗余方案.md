# rag-service 数据源去冗余方案（软链只读评估 + 可执行步骤）

> 2026-08-17。目标：消除"llmwiki 一份 + rag-service 副本一份"的冗余，评估软链只读方案并给出执行步骤。

---

## 1. 现状与冗余点

| 数据源 | 源位置 | rag-service 副本 | 冗余 |
|---|---|---|---|
| llm-wiki-methods | `/root/ubuntu-manage/llm-wiki/docs` | `/var/lib/rag-service/knowledge/llm-wiki-docs` | 一份数据两份存储 |
| system-wiki | `/llm_wiki/wiki/wiki` | `/var/lib/rag-service/knowledge/system-wiki` | 同上 |

**问题**：llmwiki 更新后，rag-service 的副本不会自动同步（除非自动更新重建索引，但数据本身是旧副本）——知识可能不一致。

## 2. 软链只读可行性分析

**结论：部分可行，取决于"源位置 rag-service 是否可读"。**

| 数据源 | 源权限 | rag-service 可读？ | 软链可行性 |
|---|---|---|---|
| `/llm_wiki/wiki/wiki` | 755（root:root） | ✅ 可读 | ✅ **可行** |
| `/root/ubuntu-manage/llm-wiki/docs` | 父目录 `/root` 是 **700** | ❌ 读不到（父目录权限挡住，子目录 755 也没用） | ❌ **不可行** |

**关键认知**：软链（`ln -s`）只解决"路径指向"，不解决"权限"——rag-service 读取软链目标时，走的是目标目录的权限链。`/root` 700 意味着**任何非 root 进程都进不去 `/root`**，软链到 `/root/...` 必然 PermissionError（你之前遇到的正是这个）。

## 3. 推荐方案（混合，立即可执行）

### 3.1 system-wiki：软链只读（✅ 推荐）

```bash
# 1. 备份并删除副本
sudo mv /var/lib/rag-service/knowledge/system-wiki /var/lib/rag-service/knowledge/system-wiki.bak
# 2. 软链指向真实源（只读：源 755，rag-service 无写权限，天然只读保护）
sudo ln -s /llm_wiki/wiki/wiki /var/lib/rag-service/knowledge/system-wiki
# 3. 验证
ls -la /var/lib/rag-service/knowledge/
# 4. 重建索引（软链路径变化）
sudo systemctl restart rag-service   # 首启自动重建；或等自动更新
```

**效果**：llmwiki 写入 `/llm_wiki/wiki/wiki` 后，rag-service 下次增量/重建即可读到**最新数据**，无需手动同步副本。知识单一来源。

### 3.2 llm-wiki-methods（/root 下的 docs）：两个选项

**选项 A（推荐）：源移到 rag-service 可读的公共位置**

如果你的 llmwiki 方法论数据（docs）由应用写到一个公共位置（如 `/srv/llm-wiki-data/docs`），配置指向它即可。但 `/root/ubuntu-manage/llm-wiki` 若由系统应用维护且不便移动，走选项 B。

**选项 B（务实）：保留副本 + 定期 rsync 同步**

docs 变化不频繁，用定时同步保证一致：

```bash
# 同步脚本（cron 每日一次；或 llmwiki 更新后手动执行）
sudo rsync -a --delete /root/ubuntu-manage/llm-wiki/docs/ /var/lib/rag-service/knowledge/llm-wiki-docs/

# 或加 cron（需 root，装好后把下面行写入 crontab -e）
# 0 3 * * * rsync -a --delete /root/ubuntu-manage/llm-wiki/docs/ /var/lib/rag-service/knowledge/llm-wiki-docs/
```

> ⚠️ **不要**用 `setfacl` 给 rag-service 开 `/root` 读权限——改 root 家目录权限有安全风险，不推荐。

### 3.3 长期最优形态（真正单一来源）

```
/srv/llm-wiki-data/          ← llmwiki 应用写入这里（唯一数据源）
    ├── docs/                ← 方法论（原 /root/ubuntu-manage/llm-wiki/docs）
    └── system-wiki/         ← 系统 wiki（原 /llm_wiki/wiki/wiki）
rag-service datasources ──→ 直接指向 /srv/llm-wiki-data/ 下（只读）
```

- 所有消费者（llmwiki 应用、rag-service）指向同一份数据
- rag-service 只读（目录 755 + root 所有），写权限只给 llmwiki 应用
- 需迁移 `/llm_wiki`（系统服务在用，需停服务迁移）——改造较大，作为后续演进

## 4. 只读权限说明

- **软链目标 755（root:root）**：rag-service 可读、不可写 → 天然只读，无需额外 ACL
- **rag-service 索引/数据**（/var/lib/rag-service/data 下）仍是 rag-service 可写——只读约束**只针对数据源**
- 若担心软链被意外写入：可改源为 755（root 所有，rag-service 无写）即可，无需 mount --bind

## 5. 执行清单（本次推荐动作）

```bash
# ① system-wiki 改软链
sudo mv /var/lib/rag-service/knowledge/system-wiki /var/lib/rag-service/knowledge/system-wiki.bak
sudo ln -s /llm_wiki/wiki/wiki /var/lib/rag-service/knowledge/system-wiki
sudo chown -h rag-service:rag-service /var/lib/rag-service/knowledge/system-wiki   # 软链自身属主（可选）

# ② docs 保留副本 + 立即同步一次（选项 B）
sudo rsync -a --delete /root/ubuntu-manage/llm-wiki/docs/ /var/lib/rag-service/knowledge/llm-wiki-docs/

# ③ 重建索引（数据源路径内容变化）
sudo systemctl restart rag-service
curl http://127.0.0.1:8931/health          # 期望 {"status":"ok","chunks":583}

# ④ 验证 system-wiki 软链可读
curl -X POST http://127.0.0.1:8931/search -H "Content-Type: application/json" -d '{"query":"KV Cache 冷启动税","top_k":1}'
# 应命中 KV Cache 冷启动税（来自软链源）
```

## 6. 取舍总结

| 方案 | 去冗余 | 同步性 | 风险 | 推荐度 |
|---|---|---|---|---|
| system-wiki 软链 + docs rsync（本次） | 部分（system-wiki 单源） | system-wiki 实时、docs 定时 | 低 | ⭐ 本次做 |
| 全部软链 | 完整 | 实时 | /root 权限无法软链 | ✗ 不可行 |
| 统一 /srv 单一来源 | 完整 | 实时 | 需迁移系统服务，改造大 | 长期演进 |
